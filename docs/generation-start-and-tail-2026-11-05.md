# 默认参数提交与演化末段耗时

## 默认23.44度不能提交

轴倾角预填23.44度，输入元数据却沿用0.1度步长。浏览器的原生数字校验认为23.44不在允许的步长上，在提交事件到达程序前就拦截了表单；用户改成23.4后恰好能通过。服务端本身接受0～90度内的有限值，没有要求舍弃第二位小数。

修正输入步长为0.01度，保留23.44默认值。回归检查遍历各起始范围的默认控件，验证范围及原生数字输入的步长关系，不只检查单个字段是否写成某个常量。

## 末段为何慢

当前生成器采用分段近似，并非把46亿年全部用同一精度计算：

- `evolution.rs` 将最近最多120Myr交给逐格岩层输运，之前的历史走`geology::ancient_history`。
- 默认球形世界的远古网格为1442格（频率12），近期求解网格最多40962格（频率64），最后再插值到655362格的地形输出。
- 近期每个内部子步都做守恒输运、板块标签推进、碰撞阻力、地质省推进和火山事件等。为避免一步跨越太多网格，步长还受稳定条件限制，硬上限1.5Myr；界面默认10Myr记录间隔并不等于内部积分步长。此前默认样本近期实际用了1142个子步。
- 构造结束后还有地貌细化、侵蚀水文、气候反馈、冰雪、生态及保存。单靠地质时钟不能估计剩余现实时间，原有按地质年数映射的进度也不是耗时均分。

以下来自此前线上默认种子42、655362格、CPU150%预算的一次实际实时帧记录。它是观察时刻的近似差值，不是每个函数的CPU剖析，也不保证所有种子都一样快。

| 区间 | 观察到的耗时 |
| --- | ---: |
| 起点到4480Myr，远古简化历史 | 约29秒 |
| 4480到接近4600Myr，近期精细演化 | 约316秒 |
| 后续地貌、水文、气候、生态及保存 | 约62秒 |
| 合计 | 约407秒 |

约最后1000万年耗时29秒，约最后500万年耗时14秒；这说明主要差异在粗细模型切换，并不是这个样本在最后几个子步突然无限变慢。证据：`artifacts/ecosystems-final-first-complete/sphere-frames.json`，分析结果`artifacts/evolution-tail-timing.json`，本机复算脚本`artifacts/analyze_evolution_tail.py`。

本次在原实时说明中标注“远古简化演化／近期精细演化”，并显示该段进度；读取当前工程保存的总时长，短演化不虚构远古段。没有修改地质年数、积分、分辨率或最终物理结果，也没有声称这一文字修正已缩短运算时间。

## 核查边界

DSH只读调研任务`ea0db48b-b80c-482d-b389-443ef5f932f7`确认分段、内部步长与帧成本路径，主代理核对了源码和实际帧时刻。阶段权重不等于实际耗时，不能据权重断言后续气候比构造更重；这里以实际观察记录为准。预览抽样、减少只读快照复制、优化输运循环都可能在保持物理条件下改善速度，需要另做计时对照，不能把放宽稳定步长当作唯一优化途径。
