## 结论

项目已有能编译、能生成和显示星球的原型，Rust 分层、网格抽象和基础测试可以继续使用。但当前存在坐标错位、子图比例尺错误、深层继承错误、水文与板块分类错误、AI 工具循环错误，以及服务端访问控制缺失。它尚不具备“核心能力全部完成”的验收条件。

建议保留现有技术栈，先修正数据和算法，再完成使用流程，最后进行视觉打磨与正式交付。继续增加风格、图层或用归一化掩盖地形问题，会让后续返工增加。

本轮没有修改业务源码、设计文档或部署。新增本报告；构建、临时验证程序和测试数据写入构建目录及系统临时目录。未调用真实 LLM、未使用用户密钥、未在生产环境执行生成或删除操作。

## 接手后确认的需求基准

以原会话中用户最后明确的要求为准，尤其是第 533 条公开消息；它晚于 v0.2 方案中的若干设计：

- 桌面封装版是正式产品，网页端用于体验。
- 网页端锁定最低模拟精度，不允许普通用户调整服务并发。
- 网页端不永久保存用户世界，离开会话后应清理。
- AI 在用户本地浏览器运行，支持用户自填供应商与模型。
- 四层地图必须继承父图；用户应能选择实际大陆、区域和地点，而不是每次固定生成零度经纬度附近。
- 初版范围是地理生成；人文推演、世设编撰暂不纳入本次补齐范围。

原 DSH 会话最后正在处理“大陆整体海拔过高”的问题，最后一条公开说明是继续修正 `land_base`。当前源码包含这次修改，但复测表明问题仍然存在。

## 主要发现

优先级：P0 为公开提供服务前必须解决；P1 为核心功能正确性或正式交付阻断；P2 为可靠性、维护和质量问题。

### A01 · P0：其他客户端可以读取和删除世界，管理接口也没有权限边界

**证据**：`crates/tf-server/src/api.rs:211` 的删除处理没有接收或检查客户端身份；世界、地图、字段、作业和 SSE 等接口没有统一权限检查。`api.rs:94` 可直接修改全局并发。服务监听所有网卡，见 `crates/tf-server/src/lib.rs:57`。

**本地实测**：客户端 A 创建世界，客户端 B 读取、删除均返回 200。此处使用的都是临时审计数据。

**影响**：只要能够访问当前服务并获得对象 ID，就可以跨用户操作；SSE 又向所有订阅者广播作业 ID。桌面版复用同一服务时也会向局域网开放。

**改进**：建立统一的会话与对象归属校验；分享访问单独授予只读权限；管理接口仅允许管理员。桌面服务默认只绑定回环地址，并使用每次启动生成的访问凭据。仅有随机对象 ID 或自定义请求头，不能替代每个接口的权限检查。

**验收**：A/B 两套独立身份的负向测试；B 不能读、生成、取消、删除 A 的数据，也收不到 A 的 SSE。普通身份不能修改全局并发。

### A02 · P1：前端与后端同编号格子的位置不一致

**证据**：后端面内点使用 Snyder 逆投影，见 `crates/tf-grid/src/sphere_hex.rs:170`；前端使用线性插值后归一化，见 `apps/web/src/renderer/sphereGrid.ts:97`。

**实测**：同为 f=32、10,242 格，逐编号比较坐标：9,300 格偏移超过 1 公里，平均偏移约 117.08 公里，最大约 246.63 公里。这是算法差异，不是 f32 精度误差。

**影响**：模拟数据被显示在错误位置；预览、交互选区、下钻与导出的地理位置无法可靠一致。仅核对格子总数不能发现这个问题。

**改进**：先让后端输出权威网格描述和坐标，避免两套实现继续分叉；需要节省传输时，再使用共享 WASM 算法或严格一致的前端实现。保存网格版本、朝向与校验值。

**验收**：各精度档位按编号逐项核对坐标；相同经纬度的预览、正式显示、空间查询及导出落在同一格。

### A03 · P1：子图把“边长格数”与“总格数”混用，比例尺严重失真

**证据**：`api.rs:481` 计算 `width / cell_size` 后直接存入 `cells`；`child_gen.rs:36` 再对它开平方作为边长。前端 `App.vue:383` 也对 `node.cells` 开平方。

**实测**：请求覆盖宽度 4,000 公里、每格 1 公里的大陆图，接口报告 `cells=4000`、`cell_size_m=1000`；实际仅生成 63×63=3,969 格，实际格宽约 63.49 公里。

**影响**：用户看到的精度、面积和实际内容不相符；将来资源、距离和地图编辑都会建立在错误单位上。

**改进**：明确拆分 `width_cells`、`height_cells`、`cell_count`、`cell_spacing_m` 和覆盖范围。达到格数预算时，明确拒绝或返回实际调整后的精度，不能静默改变比例尺。局部网格还需统一行间距及星球半径，`patch_grid.rs` 当前使用固定地球半径。

**验收**：元数据格数等于所有通道数组长度；覆盖宽度与实际格间距满足约定；所有接口与渲染器使用同一份尺寸定义。

### A04 · P1：区域与地点未从实际父图继承，树形地图没有贯通

**证据**：`child_gen.rs:62` 无论父图层级，一律重建全球 `SphereHexGrid`；`downscale.rs:41` 以全球编号读取父图局部数组，越界时静默返回高程 0、温度 15、降水 700。`App.vue:325` 将子图中心固定为 0、0；`MapTree.vue:103` 只显示直接子节点。

**实测**：世界→大陆→区域的接口都返回完成，但区域温度几乎固定为 15～15.13℃，降水约 700～701.60，表现为默认值加细节，而不是父图气候的真实细化。非法经纬度 999、负宽度 -100，以及世界直接生成 site 也被接受并返回完成。

**改进**：为球面父图和局部父图分别实现空间采样，统一投影及有效覆盖范围；范围外采样必须明确报错或采用声明的边界策略。服务端验证四层关系、父图完成状态、经纬度与宽度。地图树改为递归，并让下钻接收实际选区。

**验收**：在不同经纬度完成世界→大陆→区域→地点；四层均可选择显示；父子边缘及海陆分类保持约定的一致性；错误参数返回 4xx。

### A05 · P1：水文算法的遍历方向错误，平底盆地也没有正确处理

**证据**：`erosion.rs:193` 的汇流累积逆向遍历上游在前的拓扑序；`erosion.rs:226` 的隐式下切反而正向遍历。`erosion.rs:93` 名称和注释写 Priority-Flood，实际是局部最低点反复扫描；遇到相等高程便停止抬升。

**实测**：四格单向河道应累积为 `[1,2,3,4]` 个格子面积，实际为 `[1,2,2,2]`。高程 `[-1,5,1,1,5]` 的测试盆地中，两个低地格均无出口，湖深仍全部为 0。

**影响**：河流流量、下切、流域、湖泊，以及依赖水文的土壤和矿藏会一起失真。

**改进**：明确拓扑顺序：汇流按上游到下游，隐式下切按下游到上游。采用真正的 Priority-Flood，并处理平坦区流向；如需保留真实内流湖，应显式表达湖泊和溢流关系，而不是把无出口格当作已处理。最后一次地形修改后重新计算水文及距海距离。

算法依据：[Priority-Flood 原论文](https://rbarnes.org/sci/2014_depressions.pdf) 支持不规则网格及六邻接；隐式侵蚀可对照 [Braun–Willett 原论文](https://doi.org/10.1016/j.geomorph.2012.10.008)。

**验收**：河道面积守恒、平底盆地、无环流向、湖泊溢出口和不同网格精度的对照测试均通过。

### A06 · P1：板块汇聚/离散判反，构造传播和单位也需重新校准

**证据**：`plates.rs:286` 使用 `(v1-v2)·normal`，法线从本格指向邻格，却在 `plates.rs:291` 将负值当汇聚。`landforms.rs:140` 扩散时始终读取没有更新的 `current`，新一圈没有成为下一轮传播源；`sum / w` 又抵消了共同的衰减因子。

**实测**：构造两个相向运动的板块，被标成 `Divergent`（离散）。单一造山边界配置扩散 6 圈，实际只有边界本格及相邻一圈出现抬升，第二圈起均为 0。

**单位问题**：源码将“50～100 米/百万年”作为真实板块速度标定，同时海底扩张又使用 50,000 米/百万年。5 厘米/年换算为 50,000 米/百万年，相差 1,000 倍。真实速率的量级可对照 [USGS 的板块运动说明](https://volcanoes.usgs.gov/about/edu/dynamicplanet/nutshell.php)。

**改进**：先用接近、远离、擦过三个最小场景固定符号约定，再统一长度和时间单位。按照实际距离传播边界影响，而不是用固定圈数代表固定公里数。板块真正移动、地壳输运和热点岛链仍应作为后续明确的模拟能力，当前静态位置上的厚度变化不能直接称为完整漂移模拟。

**验收**：三种边界分类正确；山带有预期宽度及距离衰减；不同分辨率下，同等物理范围的构造作用一致。

### A07 · P1：原会话最后的高程问题仍未解决，部分气候处理被覆盖

**证据**：`pipeline.rs:135` 在水文后又改高程，未刷新流向与距海距离。`climate.rs:52` 的洋流增温随后被 `climate.rs:53` 重新计算温度覆盖。`monsoon_enabled` 被传入但没有实际分支；冰川、大气密度、生物群系丰度等参数也没有完整接入。

**实测**：现有 `visualdiag` 示例（f=128，seed=42）陆地中位高程约 4,958 米；真实 API 经济档（f=256，seed=42）约 5,465 米，陆地第 10 百分位已约 4,938 米。前者冰盖占全星球约 18.9%、苔原约 9.5%。这些是当前实现的测量值，不能把视觉偏白仅归因于配色。

**改进**：先修 A05/A06，再追踪各阶段高程变化；不要只更换最终映射曲线。分清物理场和视觉夸张：视觉可放大山体，底层高程仍保留有单位的结果。洋流修正应保留在最终温度中；未实现的参数应明确标记。

**验收**：固定一组种子，保存各阶段高程、海陆、温度、降水与水文统计；变化超出已审阅范围时检查原因。通过对照场景验证迎风坡、雨影与洋流效果。

### A08 · P1：AI 工具调用后的对话历史格式错误

**证据**：`apps/web/src/agent/core.ts:141` 仅在模型有文字时追加 assistant；随后 `core.ts:151` 覆盖最后一条消息，但没有写入 `tool_calls`。当模型只返回工具调用时，最后一条恰好是用户提问。

**实测**：用不联网的模拟响应触发一次工具调用，第二次请求的角色变成 `[system, assistant, tool]`，原始用户提问消失，assistant 的 `tool_calls` 也不存在。

**影响**：支持严格协议校验的供应商会拒绝后续请求；宽松实现也丢失对话上下文。该问题不需要真实密钥即可发现。

**改进**：始终追加完整的 assistant 消息及工具调用记录，再按 ID 追加工具结果，不能覆盖用户消息。增加取消请求的 AbortController、流异常的收尾和工具参数验证。当前 Pi 依赖没有用于运行循环；已安装 Pi 的 `BaseModel` 明确含有 `baseUrl`，因此原会话中“Pi 不支持自定义地址，所以必须自写”的理由需要重新评估，不能当作已证实限制。

消息格式依据：[OpenAI 官方工具调用文档](https://developers.openai.com/api/docs/guides/function-calling)。

**验收**：无文字的纯工具调用、有文字加工具、多个工具、工具失败、连续追问及中途取消均有模拟协议测试；随后再由用户自行配置供应商完成实际兼容性验证。

### A09 · P1：实时连接没有启用，气候图层没有完整使用实际数据

**证据**：`App.vue:219` 与 `App.vue:249` 定义了 `startStream`、`stopStream`，项目中没有调用点。`App.vue:177` 初次生成后上传数据时漏掉温度和降水。`renderer/shaders.ts:99` 将正式数据的 `vMoist` 写死为 0.5，声明的 `aPrecipitation` 没有参与结果。

**影响**：当前入口无法获得实时阶段画面；初次生成的温度图层缺数据；降水图层即使加载了数组，也会显示常量对应的颜色。重新选择地图有可能补上温度，但不能修复降水。

**改进**：以当前作业 ID 管理订阅生命周期；统一生成完成与选择地图时的数据加载路径；图层直接使用真实字段及明确的归一化规则。同步更新 `currentMap` 与字段数据，避免 AI 统计旧地图。平面模式还需接通气候字段及实际缩放/平移。

**验收**：一次完整生成能看到中间帧；两个并行作业不串画面；地图切换后各图层与服务端抽样数值一致；完成后正确退出预览。

### A10 · P1：取消、失败、并发与恢复的状态不可靠

**证据**：`generate.rs:100` 取消后返回 `Ok(())`，`jobs.rs:229` 将其写成 done。取消检查在回调中仅提前返回回调，没有终止模拟。`jobs.rs:117` 调低并发不回收许可，反复执行 1→8→1 会不断增加实际许可数，显示上限与真实调度上限逐渐脱离；失败分支没有同步更新地图状态。`store.rs:274` 的活动作业查询没有恢复调用者。

**实测**：运行中取消返回 `ok=true`，约 14.24 秒后作业状态为 done，地图仍为 pending。空闲时系统状态也报告 `active_jobs=1`，因为它读取的是配置上限，见 `api.rs:80`。

**改进**：生成结果明确分为成功、取消、失败；取消信号进入实际循环。作业与地图使用一致的状态转换，持久化失败必须可见。调低并发后阻止新作业超限启动；进程重启时恢复或明确终结遗留任务。SSE 丢事件后应能够用状态快照恢复。

**验收**：运行及排队取消均最终为 cancelled；失败不会留下 pending 地图；8→1 调整后新调度遵守 1；重启、断线和写盘失败的状态可解释。

### A11 · P1：桌面启动路径与打包资源没有接通

**证据**：`src-tauri/src/main.rs:47` 将窗口导航到本地 HTTP 根路径，但没有设置 `TF_STATIC_DIR`；服务端仅在该变量存在时挂载网页。构建前端固定使用 `/map/` 路径，见 `apps/web/vite.config.ts:7`。打包前构建命令为空，见 `src-tauri/tauri.conf.json:9`。

**验证**：为隔离服务手动提供静态目录后，`/` 返回 200，但 `/map/` 和 `/map/assets/...js` 返回 404，资源实际挂在 `/assets/...js`。这已能证明路径不一致；尚未启动安装包验证具体窗口症状。

**改进**：明确选择 Tauri 内置资源协议加动态本地 API 地址，或者由本地 HTTP 服务完整提供页面与匹配路径。启动时做健康检查，使用确定的数据路径与日志；构建安装包前自动生成正确的前端产物。默认精度和并发应适应设备，不能固定最高档和两个大任务。

**验收**：干净安装后脱网启动、创建世界、重启读取、导出、退出均通过；不依赖开发目录、Vite 服务或手工环境变量。

### A12 · P1/P2：网页临时会话要求未落地，删除后仍留存数据

**证据**：`store.rs:172` 删除世界时只删 worlds 表，不删除地图、作业与 fields；项目没有会话心跳、失效时间、退出回收或后台清理实现。

**实测**：删除审计世界后，其地图高程接口仍返回 200。相同世界种子重新生成的世界层数据逐字节一致，但相同位置的两个大陆子图有 3,719/3,969 个高程值不同，原因是子种子依赖随机父图 ID，见 `api.rs:488`。

**影响**：网页数据会持续积累，与“离开会话就删除”冲突；仅删除世界记录也没有释放字段数据。子图按需重算缺少稳定的位置身份，导出 JSON 没有完整记录空间描述、算法版本及局部派生参数，不能视为完整可恢复工程。

**改进**：桌面工程持久保存，网页体验按会话租期管理；主动结束立即清理，异常退出由心跳失效后的短宽限期兜底。级联取消任务并删除关联数据。以稳定选区和生成版本派生子种子，保存完整工程描述及编辑增量。

**验收**：会话结束后逻辑数据被清除；删除期间作业不能回写出孤儿数据；相同工程重新生成同位置子图可复现；导出再导入能恢复空间关系及字段。

## 其他需要补齐的事项

- **资源预算**：`TF_QUALITY` 未设置时没有服务器默认强制上限；任务队列没有每会话配额。PNG 最大 8192²，仅一个 RGB 缓冲即 192 MiB，编码还会复制多份，且使用不压缩的 stored 块。应在接口层限制内存、队列与导出并发，并在阻塞线程中执行重工作；具体峰值需另行压测。
- **数据完整性**：12 个通道逐个事务写入，缺少完整快照提交标记；矿藏、板块归属与部分生成信息没有随世界一起持久化。应以完整地图快照发布，失败清理临时结果。
- **安全描述**：当前代码路径确实将 LLM 密钥发给用户选择的供应商，而非本项目后端；但“网站绝不可能获取浏览器中的密钥”是过度承诺，同源网页脚本仍可读取 localStorage。应使用准确说明，提供仅本次会话保存选项，评估脚本来源与 CSP。
- **工程管理**：当前目录没有 Git 元数据，也没有可见 CI。README 仍写 51 个测试、导出和桌面版未做，与代码不符；v0.2 仍有过时的 Node sidecar 与长期保存策略。应建立可回退基线、自动检查和可追踪的需求清单。
- **设计流程**：目前没有独立的 `docs/frontend-design.md`。后续前端修改前应先确认现有风格是否沿用并形成文档；新增或大幅调整布局时先提供预览，审阅通过再实现。本轮仅审计，未替用户定稿设计。

## 建议的实施顺序与验收门槛

### 第一步：封住访问风险，建立可回退基线

处理 A01，分离管理员和普通会话，桌面服务仅绑定本机；锁定网页资源预算。建立 Git 基线及自动构建检查，把本报告中的最小反例变成有意义的回归测试。核对实际线上部署配置后再决定生产处置。

**完成条件**：跨用户操作全部被拒绝；普通用户不能改变服务限制；后续每次修改都能回退。

### 第二步：统一地图的数据定义与空间关系

优先处理 A02～A04 和 A12 的稳定身份部分。保留 `GridOps` 抽象，增加明确的球面/局部网格描述及采样接口；前端、导出、子图从同一权威几何获取位置。不在各个渲染入口分别猜格数和投影。

**完成条件**：四层地图的编号、位置、实际格宽、父子边界、重生成结果均一致。此阶段先保证正确，不以高帧率掩盖位置错误。

### 第三步：修正成因链并建立可量化的模拟基准

按 A06→A05→A07 的依赖顺序修复构造分类、传播、水文及气候；为每个阶段保存统计与诊断输出，区分物理数据和美术显示。明确哪些是物理近似，哪些能力尚未实现。

**完成条件**：最小物理场景正确；固定种子集合的统计变化可解释；最终高程与水文、距海、生态一致。不能只靠最后把海拔和降水强行映射到预设分布来通过验收。

### 第四步：完成使用流程与 AI 工具闭环

处理 A08～A10：统一地图状态、生成订阅、字段加载、取消与恢复。选择实际选区，递归展示地图树，修复各图层，再补充参数设置、地图选择与错误恢复。先恢复现有 7 个工具，再逐个增加编辑工具及撤销能力。

**完成条件**：一次操作完成“配置→生成中查看→下钻→切图层→AI 查询→导出”；中断、断线、失败不会卡住或误报成功。前端工作遵循风格确认、设计文档、布局预览与审阅流程。

### 第五步：优先交付桌面正式产品，再完善网页体验

处理 A11 及完整工程保存/恢复；以实际安装包验收，不依赖开发环境。网页版落实临时会话清理、下载引导和资源配额。地下层、覆盖层、更多风格和人文接口在上述门槛通过后逐项展开。

**完成条件**：干净设备安装与离线使用通过；工程可保存、重开、导入导出；网页体验数据按约定清理。Windows 通过不等于 macOS/Linux 已通过，应分别列出平台验证状态。

## 后续工作原则

不建议重写整个项目或更换 Rust/Vue/redb/Tauri。真正需要重整的是空间数据契约、模拟正确性、作业状态和产品验收方式。每个里程碑都应以可复现的输入、数据和实际操作作为证据，再更新完成状态。
